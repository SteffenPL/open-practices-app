# Link tools from the practice text

A reader should be able to learn a practice from its title and key message. Requiring authors to build decision trees made a passing reference to a tool as expensive to write as a full setup guide. Authors now mention a shared Tool by typing its handle in the message and choosing it from autocomplete. A Practice can have zero Tools. Repeated mentions of one Tool share a single setup entry.

Authors decide whether to include each mentioned Tool in their Install List. They may use a suggested command, change it, or add just a setup note. The Practice keeps its own copy of approved commands and notes. Updating a Tool’s suggested command therefore leaves published instructions intact.

A Tool can represent a conventional CLI or an APM package. An exact APM package path identifies one package, while a shared repository or website can host several tools. When identifiers suggest a duplicate, the contributor decides whether to use the existing entry, merge, or keep distinct tools. A merge preserves references to the original handles. Signed-in users can contribute edits, and readers can inspect the revision history.

Backticks mark code in prose. Paired straight or curly double quotes mark prompts. A hash inside code or a prompt stays literal. For example, the practice text “Ask #tool-name to summarize this change” inside prompt quotes does not add a Tool.

Existing Practices keep their URLs. Descriptions of alternatives remain readable as notes. An old list of alternatives does not authorize running every command in it. The same preservation rule applies when importing older Practice Definitions.
